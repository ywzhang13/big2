# 聊天與互動：API 和事件格式（給老馬）

老柯 2026-11-13，分支 `feat/mj-chat-history`。

> **第二版（審伯必修修正後）對前端的影響，只有兩點：**
> 1. 觀戰頻道改成**每位觀戰者各自一個**，綁這一場。前端照舊用歷史 API 回傳的 `spectatorChannel` 去訂閱就好，名稱格式不變。
> 2. 文字和語音送出時，如果房間剛好在那一瞬間被關掉，會回 **`410 room_closed`**。前端當成「房間已關閉」處理就好。

老闆的要求：
- 聊天訊息保存在這一場，按聊天時要有聊天框的感覺。
- 觀戰的人可以看聊天、看互動。
- 聊天和互動拉成麻將、大老二、十三支三個遊戲共用；大老二這次先不接。

目前只有麻將接上。格式定義在 `lib/social/events.ts`，十三支和大老二之後照同一份格式送，前端的聊天框和互動特效元件就能共用。

## 1. 訊息格式

### ChatMessage（一則聊天）

即時事件和歷史 API 用的都是這個格式：

```ts
{
  id: string;            // 伺服器給的 uuid。即時事件和歷史可能各收到一次，用 id 去重
  kind: "text" | "voice";
  from: string;          // 發送者的 playerId，伺服器依登入帳號認定
  fromName: string;
  fromSeat: number;      // 座位 0～3
  text?: string;         // 文字。快捷短語也放在這裡，另外帶 phrase
  phrase?: string;       // nice／wait／hurry／thanks
  url?: string | null;   // 語音的播放網址，約 1 小時有效
                         // 歷史 API 每次都會重新簽發；語音檔已被清掉（超過 24 小時）時是 null，畫面顯示「語音已過期」
  durationMs?: number;   // 語音長度
  ts: number;            // 伺服器時間（毫秒）
}
```

### EffectEvent（一次互動特效）

格式和原本一樣：

```ts
{ id, effect: "heart"|"money"|"egg"|"water"|"punch"|"clap", from, fromName, fromSeat, to, toName, toSeat, ts }
```

## 2. 即時事件（Realtime broadcast）

| 事件 | payload | 送到哪裡 |
|---|---|---|
| `mj_chat` | `{ playerId, message: ChatMessage }` | 同桌四人各自的座位頻道，另外每位已同意的觀戰者各送一份到他自己的觀戰頻道 |
| `mj_effect` | `{ playerId, effect: EffectEvent }` | 同上 |

- 座位頻道沿用原本的，`payload.playerId` 是收件的座位。
- **觀戰頻道是新的**，送到這裡的事件 `payload.playerId` 都是 `"*spectators"`，前端可以直接忽略這個欄位。
- 每一則都會重新查一次同意名單。觀戰者的同意被收回後，下一則就不會再送給他。
- 公開頻道 `mj-<房號>` 收不到聊天和互動，這點和原本一樣。

## 3. 讀歷史：`GET /api/mahjong/chat/history?roomId=<房間 id>`

- 要帶登入：`Authorization: Bearer <token>`。
- **什麼時候呼叫**：進房、重新整理、斷線重連、觀戰開始時各呼叫一次，用來補齊歷史。打牌當下不用呼叫，新訊息會從即時事件收到。

200 回傳：

```jsonc
{
  "roomId": "…",
  "limit": 200,                    // 每房最多保存的則數
  "role": "player" | "spectator",
  "messages": [ChatMessage, …],    // 由舊到新
  "spectatorChannel": "mj-5878-s-…" // 只有觀戰者會拿到
}
```

### 誰可以讀

- **同桌玩家（含訪客）**：可以讀。
- **觀戰者**：在這房至少被一位玩家同意觀戰，才能讀。讀到之後：
  1. 訂閱回傳的 `spectatorChannel`，就能即時收到 `mj_chat` 和 `mj_effect`。
  2. 這是**他自己的**頻道：用這一場（房間 id）加上他的帳號，再用伺服器金鑰算出來，別人猜不到。
  3. 房號之後被重用開新場，頻道名稱也會跟著換，所以舊場的觀戰者收不到新場的訊息。
  4. 要放在牌局狀態用的 `mj-<房號>` 公開頻道之外，另外再訂閱這一個。
- **為什麼每人各一個頻道**：Realtime 的廣播頻道用公開金鑰也能發訊息。每人各一個頻道，觀戰者就算往自己的頻道發假訊息，也只有他自己看得到，騙不到其他觀戰者或玩家。

| HTTP | error | 什麼時候 |
|---|---|---|
| 400 | `bad_request` | 沒帶 roomId |
| 401 | `not_logged_in` | 沒登入 |
| 403 | `not_allowed` | 不是同桌玩家，也不是被同意的觀戰者（只申請、還沒同意也算） |
| 404 | `room_not_found` | 房間不在。關房時聊天紀錄會一起刪掉 |
| 500 | `server_error` | 伺服器錯誤 |

## 4. 發言和丟互動

API 沒有改：
- 文字：`POST /api/mahjong/chat`
- 語音：`POST /api/mahjong/voice`
- 互動：`POST /api/mahjong/effect`

格式、冷卻、錯誤碼都和原本一樣。

- **觀戰者**：不能發言、不能送語音、不能丟互動，三支都回 `403 not_in_room`。前端在觀戰頁不用顯示輸入框和互動按鈕。
- **成功送出的訊息**：會存進這房的聊天紀錄。被冷卻擋下（429）的訊息不會存。
- **新增錯誤 `410 room_closed`**（只有文字和語音會出現）：送出的同時房間剛好被關掉，這則不存也不送。如果房間在送出之前就已經關了，照舊回 `404 room_not_found`。

## 5. 保存規則

| 項目 | 規則 |
|---|---|
| 保存範圍 | 這一間房、這一場 |
| 則數上限 | 每房只留最近 **200 則**，超過就刪最舊的。一則約 200 bytes，200 則約 40 KB |
| 關房 | 聊天紀錄、語音檔、冷卻紀錄一起刪掉 |
| 保底 | 房間已經不在、關房時漏刪的紀錄，會在之後任何一則寫入時順手清掉。還開著的房間不受影響，開再久也不會被清 |
| 關房後晚到的訊息 | 一律擋下，不會再寫進紀錄 |
| 同時寫入 | 同一間房的寫入和 200 則裁切會排隊進行，不會多刪或少刪 |
| 語音檔 | 關房就刪；房間還開著的話最多留 24 小時，跟原本一樣 |
| 互動特效 | 不存歷史，只有即時事件 |

## 6. 對牌局速度的影響

- **文字**：發言時「檢查冷卻、存檔」用同一個 SQL 函式（`mj_chat_post`）。另外會同時查一次同意觀戰名單，兩個請求並行送出，所以不會多等。
- **語音**：多一次寫入（`mj_chat_append`）。語音一則最少間隔 2 秒，而且是在轉檔之後才寫，影響很小。
- **牌局本身**：聊天不碰牌局狀態，牌局版本號不會變，前端不會因為聊天而重抓牌局。
